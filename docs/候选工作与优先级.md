# 候选工作与优先级

> 截至 **2026-09-29**。这张表是"下一步做什么"的备查清单，每条都带上收益/成本估计与**怎么验收**。
> 做掉一条就把结论挪到文末的「已排除 / 已验证」里。

## 换算基准（后面所有收益估计都由这两条推出来）

1. **深度 → 棋力**：难度阶梯实测「**2 层 ≈ 净 +20 局 / 40 局**」，即 **1 层 ≈ +100 局 / 400**。
2. **时间 → 深度**：节点数每层约 ×1.8，所以 **10% 时间 ≈ 0.16 层 ≈ +16 局 / 400**。
3. **工具分辨率**：`--suites` 的 95% 区间，**4 套件（400 局）约 ±10**、**6 套件（600 局）约 ±5**。
   低于这个量级的效应测不出来，只能用"实际层数"（`npm run level:budget`）旁证。

当前 profile（8 个 d8 搜索，总采样 2681ms）：`evaluate` **42.3%**、`isChecked` 15.9%、
`genPseudoMoves` 14.6%、`scoreMoves` 6.9%、`genLegalMovesInPlace` 6.8%、`negamax` 6.3%。

## 前几项说明

### ① `isChecked` 细化（15.9% → 目标 ~8%）

现在的快路径要求「起点和终点都不在将线上」，比较保守。可以再分两类放宽：

- **终点**在将线上：只有敌方**炮**才可能因此形成炮架 → 若那条线上没有敌炮，直接放行
- **起点**在将线上：只有它是「将朝某方向遇到的第一个子」时才可能挡线 / 当炮架 → 查一次射线即可

**验收**：`/tmp/legal-crosscheck.js` 那套交叉验证（6903 个局面与"每个着法都走子再全盘扫描"
的参考实现逐个对齐）+ 全量测试 + `level:budget` 的实际层数。

### ② `match.js` 等时模式（性价比最高的一项，因为它解锁其它项）

现在对抗**全是固定深度**（`deterministic` 模式下时限是 `Infinity`），所以速度收益在对抗里
完全体现不出来——这两轮提速只能靠 `level:budget` 的"实际层数"旁证。

加一个 `--equal-time`（用档位时限而非固定深度，配合 `--suites` 多套件统计）之后，就能直接
回答"更快的引擎等时是不是更强"。

**注意**：早年试过"等时对抗 8 局"，结论完全不可信（同引擎自对弈都能打出 4 胜 1 和 3 负）。
必须配 `--suites`（≥4 套）与统计判读才有意义。

### ③ LMR / futility 等时调参

这两者的价值**全在"等时更深"**上——固定深度下测不出（甚至略负），这是文档里已记的教训，
但参数从没在**等时条件**下系统扫过。这是唯一还没被系统试过的搜索侧旋钮。

**验收**：`--equal-time` + `--suites 4`（需先做 ②）。

### ④ 评估（42.3%）

最大的一块，也最不好动：上一轮试过的"子力协调"项**回退了**（多套件复核是 −3，见 README），
说明评估已接近局部最优。可行的只有"分档计算"这类结构性改动（例如 quiesce 用廉价评估），
风险是变弱。

### ⑤ 自动调参

理论收益最大，但用对抗做目标函数一次评估要 ~20 分钟，坐标下降扫 10 个参数就是十几小时。
要做就得先造一个**更快的目标函数**（低深度自对弈、或与深搜的着法一致率）。

## 建议顺序

**先 ② 再 ①**——②是工具，能把"提速"从"只能旁证"变成"可直接测量"，之后 ①②③⑤ 都能用它验收。
③④⑤ 收益不确定，值得试但要控制投入。
