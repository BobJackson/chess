# 松风桂月（微信象棋小游戏）

> 松风起，桂子落，来一盘。—— 松树与桂花的象棋。

一个运行在**微信小游戏**上的中国象棋：人机对战（五档难度）、本地双人、好友联机（云开发 / 自建 WebSocket 中继）。

核心设计原则：**对局逻辑、棋盘渲染、触摸状态机、联机会话全部是纯 JavaScript**，不依赖小游戏/小程序的页面 API，因此都能在 node 下直接单元测试；只有最外层的"场景外壳"（自绘 UI + 全局触摸 + 主循环）与小游戏环境耦合。

> 历史版本：本项目曾以**小程序**（pages + WXML）形态实现，完整保留在 git 分支 `miniprogram-version`。因发布账号为小游戏类型，主干已改造为小游戏形态。

## 小游戏与小程序的差异（本项目的应对）

| 小程序有、小游戏没有 | 本项目的替代方案 |
|---|---|
| `app.json` + `pages/` 路由 | `game.json` + `scenes/` 场景状态机（`scenes/manager.js`） |
| WXML/WXSS 组件（button/input…） | Canvas 自绘组件（`ui/widgets.js`）+ 命中测试 |
| `Page()` 生命周期 | 场景协议 `onEnter/onExit/onTouch/render/shouldRender` |
| `input` 输入框 | `wx.showKeyboard` 软键盘（大厅录入房间号） |
| 组件级 `bindtouchstart` | 全局 `wx.onTouchStart/Move/End/Cancel` 分发到当前场景 |

## 快速开始

1. 用微信开发者工具导入本目录（`project.config.json` 所在处），`compileType` 已为 `game`。
2. `project.config.json` 的 `appid` 需为**小游戏类型**账号（本项目即因账号为小游戏而采用此形态）。
3. 人机 / 本地双人：直接编译即可玩，无需后端。
4. 好友联机：见下「云开发配置」。

## 云开发配置（好友联机）

1. 开通云开发（小游戏同样支持 `wx.cloud`）。
2. 创建集合 `chess_rooms`（`_id` 为房间号，`{creator,createdAt}`）与 `chess_msgs`（`{room,clientId,type,...}`），权限「所有用户可读写」。
3. 多环境时在 `game.js` 的 `wx.cloud.init({ env:'环境ID' })` 指定。
4. 一方「创建房间」得 4 位房间号 → 另一方输入加入 → 建房者执红。
5. **邀请好友**：等待态点「邀请好友」生成微信分享卡片（`query=room=房间号`）；好友点卡片启动时 `onShow` 捕获房间号，自动进大厅加入并直接进入对局，无需手输。
6. 房主「取消房间」或退出时会删除房间登记（`removeRoom`），避免垃圾房间堆积；建房遇房号冲突自动换号重试（最多 3 次）。

联机协议见 `net/session.js`：`join/welcome/move/stateReq/state/result/bye`；走法只传 `(from,to,ply)` 本地校验重放，乱序自动全量重同步，同 `clientId` 重加入即断线重连。

## 自建服务器联机（免云开发费用）

有备案域名与服务器时，可改用自建 WebSocket 中继，**零云开发费用**：

1. **部署中继**：把 `server/` 目录上传服务器，`node room-server.js 8787`（零第三方依赖；建议 pm2/systemd 守护）。
2. **nginx 反代 wss**（证书用你已有的）：仓库已提供现成配置 `deploy/nginx/chess.wangyousong.com.conf`（含 80→443 跳转、`/ws` 升级头与长超时、`/healthz` 健康检查），拷贝到 `/etc/nginx/conf.d/` 后 `nginx -t && nginx -s reload`。手动配置参考：
   ```nginx
   location /ws {
     proxy_pass http://127.0.0.1:8787;
     proxy_http_version 1.1;
     proxy_set_header Upgrade $http_upgrade;
     proxy_set_header Connection "upgrade";
     proxy_read_timeout 3600s;
   }
   ```
3. **mp 控制台**：「开发设置 → 服务器域名 → socket 合法域名」添加 `wss://chess.wangyousong.com`。
4. **切换通道**：编辑 `miniprogram/net/config.js`（当前已配置为真实域名）：
   ```js
   module.exports = { kind: 'ws', wsUrl: 'wss://chess.wangyousong.com/ws' };
   ```
   `kind: 'cloud'` 则走微信云开发。大厅/对局代码无需改动（传输工厂按配置选择适配器）。
5. 服务端只做**按房间广播中继**（握手 URL `?room=` 登记房间），不解析棋局、不做裁判；校验与重同步均在客户端 `net/session.js` 完成。

### Docker 部署（服务器已有 Docker 时推荐）

```bash
docker build -t chess-room ./server
docker run -d --name chess-room --restart unless-stopped -p 127.0.0.1:8787:8787 chess-room
# 或用编排（仓库根目录）
docker compose up -d
```

- 镜像基于 `node:20-alpine`、仅复制两个运行文件、以非 root 用户运行；端口经 `PORT` 环境变量配置（默认 8787）
- 端口只绑定 `127.0.0.1`，对外仍由 nginx 以 `wss://你的域名/ws` 反代（见上）
- 部署后冒烟验证（两个裸 WS 客户端验证同房间广播与跨房间隔离）：
  ```bash
  npm run smoke:ws            # 默认连 ws://127.0.0.1:18787/ws，可传参改地址
  ```

## 音频与沉浸感

- **BGM 双曲目**：《松风》（`bgm-songfeng.m4a`，58.4s）与《桂月》（`bgm-guiyue.m4a`，38.7s），设置页「配乐」自由切换，当前曲目持久化；均做无缝循环（等功率交叉淡化接缝）。`InnerAudioContext.loop` 循环，切后台自动暂停、回前台恢复；受 iOS 限制在**首次触摸**后启动。
  - 《松风》：`npm run gen:bgm`（`scripts/gen-bgm.js`）纯数学合成——D 宫五声音阶 66BPM，古筝拨弦（失谐泛音+长音揉弦）+ 琶音 + 低音拨弦 + 箫垫底，A/B 两段；输出 WAV 后用 afconvert 编码（脚本末尾有提示）。
  - 《桂月》：原实录素材修复版（裁 25s 静音尾 + 1.5s 交叉淡化循环 + 峰值规范化）。
- **音效**：`audio/*.wav` 由 `npm run gen:sfx`（`scripts/gen-sfx.js`）纯数学合成，无外部素材——落子木质"笃"、吃子闷响、将军两声警示钟、胜/负五声琶音与低锣、按钮轻击、悔棋上挑。
- **开关与设置**：系统设置页（菜单「系统设置」按钮，位于查看规则之下）统一管理：音乐开关 / 配乐切换 / 音效开关 / 先后手 / 主题（松桂·紫金夜）；开关、曲目与主题选择用 `wx.setStorageSync` 持久化。
- 重新生成音效：`npm run gen:sfx`；新增 BGM 曲目：放入 `audio/` 并在 `ui/audio.js` 的 `BGM_TRACKS` 加一行，设置页配乐选项自动跟随。
- **绝杀语音**：`audio/mate-<key>.m4a`，终局判出杀法时把名字念出来（不只是弹窗显示）。由 `npm run gen:voice`（`scripts/gen-mate-voice.js`）用 macOS 自带的 `say` + `afconvert` 合成，11 条约 88KB；清单以 `core/mate.js` 为单一数据源，改名只需重跑脚本。音频按需创建上下文，不在启动时占用。

## 先后手（让先）

设置页「先后手」分段：默认**执红先手**，可选**让先执黑**（人机/本地生效；联机由房间分配，房主执红）。

- 人机执黑：AI 执红自动先走，棋盘整盘翻转为黑方视角；悔棋若悔回开局会自动重新调度 AI，不会卡局。
- 本地双人执黑：松执黑，账本按松的边记（黑胜记松）。

## 松桂账本

二人专属的胜负账：只记「人对人」的局（人机是练棋，不入账），本机 `wx.setStorageSync` 持久化，主菜单展示「松 12 : 9 桂 · 和 2」与最近一局结果。

- **本地双人**：默认红 = 松、黑 = 桂；设置页选「让先执黑」则松执黑，按松的边记
- **好友联机**：本机方 = 松，对方 = 桂（账本各存各的，各记各的视角）
- 实现在 `core/ledger.js`（纯 JS 可单测，存储失败降级内存账）；终局时在 `scenes/board.js` 的 `showResult` 记账，每局只记一次。

**账本详情页**：主菜单比分行可点（带 › 提示），进入独立场景——大比分、当前连胜（同一人连赢 ≥2 局、和棋断连）、逐局历史列表（日期/模式/胜负 + 结果文案，最新在上，可拖动滚动）。逐局历史存最近 50 局（FIFO），旧账数据无此字段自动兼容、从下一局开始积累。

## AI 分片搜索（不冻屏）

高难度（困难 8 层 / 大师 10 层）的搜索不再整段阻塞主线程。`core/ai.js` 在同步 `findBestMove` 之外提供 `createSearch`：同一套迭代加深 + Alpha-Beta，但拆成「每次一个根走法」的小步，每片最多 12ms（`scenes/board.js` 的 `AI_SLICE_MS`）就让出主线程渲染「AI 思考中…」，下一帧接着搜。单个根走法在片内搜不完时沿用上一层迭代的分值，保证每层必然收尾。实测大师档中局：旧版整段冻结约 4.5s，分片后单片最长约 13ms（一帧预算内）。「提示」按钮同样走分片。AI 思考中悔棋 = 取消 AI 并撤回刚走的一手；重开/离场自动取消未完成的搜索。

## AI 置换表（TT）

`core/position.js` 用 Zobrist 随机表在 `makeMove/unmakeMove` 里 O(1) 增量维护 `pos.hash`；`core/ai.js` 的搜索上下文持一张 2^16 槽的置换表（EXACT/LOWER/UPPER 三旗标、杀棋分按 ply 折算、深度优先替换），命中走法还参与排序（优先级高于 PV 走法）。效果：同等深度节点数大降（中局 depth 6 约 -36%、depth 8 约 -52%），相同时间内大师档可多搜近一层；走法与分值与无 TT 完全一致（有对照测试）。选项 `noTT: true` 可关闭置换表供对照。

## AI 重复局面判定（不变作和 / 长将判负）

搜索里维护一条「路径栈」：每层记下该节点的 Zobrist 哈希与「刚走的这一手是否将军」。同型局面（盘面 + 走子方相同）在搜索路径上第二次出现时，直接按 `core/game.js` 的终局规则给分——循环段内单方每手都在将军而对方没有 → 该方**长将判负**（给杀棋分）；否则**双方不变作和**（给 0 分）。判定在置换表之前完成，且重复分不进置换表（它依赖路径）。

为什么必须有：没有它的时候，引擎会把「走回去」当成新变化反复计算，于是出现**走一步、下一步又撤销自己**的往返走子；静止局面下分值在相邻两层之间来回摆动（实测同一线路差 457 分），引擎跟着来回改主意，对手则在旁边白吃子力。有了它之后，优势方不会主动走进重复和棋（0 分低于它的优势分），劣势方会主动争取和棋，长将线路更是会被直接判负避开。

只认搜索树内的循环（含「走回根局面」）：循环段每一手是否将军都看得见，长将才判得准；分值也不依赖对局外的信息，对局、提示、局面分析各调用方行为一致。单次搜索的开销约 +5%（每节点一次 `isChecked`）。

## 难度强度基准（scripts/bench-levels.js）

`npm run bench:levels` 打印五档在开局/中局两个局面上的实际完成层数、节点数、耗时与选招；加 `--games N` 还能让大师档执黑跟各档位自对弈 N 局（走产品同款 `createSearch` + `Game` 全流程，含三次重复/长将/自然限着判定），输出战绩汇总。`--check` 顺带断言走法合法、对局正常终局、搜索不污染局面。改动评估函数、搜索或难度参数后跑一遍，比读代码可靠。

实测（2026-09-27 走法排序 + LMR + 空着裁剪 + 机动性评估之后）：大师档在 4.5 秒预算内**开局、中局都能跑满标称的 8 层**（开局 8 层约 2.6s / 314 万节点，中局 8 层约 1.2s / 133 万节点）；困难档 6 层只要 0.5s。改造前的数字是：开局 6 层、中局 6–7 层（depth 8 开局需 37s，根本跑不完）。

实测（**2026-09-28 把大师档上限提到 10 层之后**）：开局 8 层 / 2.6s（9 层在 4.5s 内跑不完），中局 **9 层 / 3.7s**。见「难度档位的深度上限重定」一节。

### 对抗测试的方法学（2026-09-27 修正）

评估/搜索的改动到底有没有变强，只能靠对弈。早先用的"等时对抗（产品路径 `createSearch`，1500ms/步，8 局）"**样本太小**——同引擎自对弈都能打出 4 胜 1 和 3 负（净 +1），小幅改动（净 ±10 以内）根本读不出来；上一轮"2格 7 胜 1 负"的结论就是被它误导的（换成下面的方法后是**净 0**）。

现在用 `npm run match`（`scripts/match.js`）：在 **59 个随机局面**上、**固定深度**、关闭一切随机化对弈，正反两色各一局共 118 局，结果完全可复现——同引擎对照**恒为净 0**。用法：先 `node scripts/match.js --save /tmp/before` 存一份对照，改完代码再 `node scripts/match.js /tmp/before`。判读：净 ≥ 10 才算有信号，净 < 10 视为持平。

### 历史结论复核：逐项消融（2026-09-27）

上面几节的结论早年大多是用"等时对抗 8 局"得出的（那个工具有 ±10 局噪声）。本轮把**每一项特性单独关掉**做成对照版本，用 `npm run match` 测"当前版本净胜多少"（固定深度 6、45 局面 × 正反两色 = 90 局；同引擎对照净 0）：

| 关掉的特性 | 净胜局 | 节点代价（开局/中局） | 判读 |
|---|---|---|---|
| **根走法择路（`bound` 标记）** | **+116**（118 局，深度 6）/ **+109**（深度 5） | 1.00× / 1.00× | **项目史上最有价值的改动** |
| 重复局面判定 | **+11** | 0.82× / 1.00× | 确有价值 |
| 置换表（TT） | +4 | 1.08× / 2.06× | 速度特性 |
| 将帅威胁九宫 | +3 | 0.87× / 0.83× | 测不出价值，还多花节点 |
| 不甘心和棋（−120 改 0） | +2 | 0.82× / 1.00× | 测不出价值 |
| 缺士怕车 / 缺象怕炮 | −1 | 1.00× / 1.00× | 测不出价值（也不花代价） |
| 晚走法削减（LMR） | −1 | **2.04× / 2.15×** | 速度特性 |
| 空着裁剪（NMP） | −1 | 1.05× / 1.15× | 速度特性 |
| 全排序（退回只排前 12 手） | −8 | 0.74× / 1.28× | 测不出价值 |

（节点代价 > 1 表示关掉后节点变多，即该特性省节点。**这一列是单个开局/中局局面测的，只作参考**——2026-09-28 复核发现单局面节点数受剪枝混沌影响很大，换一批局面结论可能反过来，见下面「节点代价怎么测」。）

三条要紧的结论：

1. **根走法择路修复是项目史上最有价值的改动**：关掉它，当前版本 **116 胜 2 和 0 负**。关掉后的引擎分值一路虚涨（实测开局前 8 手报 11 → 47 → −51 → 107 → 178）却下出无意义的着法（兵九进一、兵五进一…）——正是当年"上界中选"的病灶。**当年那次"修复后 0 胜 6 负"的等时对抗结论完全错了**（6 局样本 + 对照版本还差着别的特性），第四轮记的"悬案"至此了结。

2. **速度类特性（LMR / NMP / TT）在固定深度下都测不出棋力差**——这是应该的：它们靠剪枝/记忆省节点，代价是同等深度精度略降，两者相抵。它们的价值在**节点数**上：LMR 省一半以上节点（2.04×/2.15×），按本引擎约 2.6× 一个分支因子折算 ≈ **多算 0.74 层**，而"多一层"实测值 **净 +49**；TT 在中局省一倍节点（≈ +0.76 层）。所以等时下它们是净赚的。

3. **评估函数里的"将帅安全"两项（威胁九宫、缺士怕车）测不出可靠价值**：威胁九宫关掉后，深度 6 是 **+3**（90 局）、深度 7 是 **+10**（48 局）——都在噪声带内或刚踩线；缺士怕车/缺象怕炮关掉后是 **−1**。当年这两项是用 4 局等时对抗（"2 胜 1 和 1 负"）验证的，那个样本量等于没有。**2026-09-28 复核补充**：当时说威胁项"多花 13~17% 节点"是单局面测的，换成 50 局面套件只有 ±3%，**节点代价不成立**——所以两项都保持原样（见下）。

### 节点代价怎么测（2026-09-28 修正）

评估项"贵不贵"必须用**一批局面**测，`npm run node:bench`（`scripts/node-bench.js`，5 个开局 + 45 个中局，固定深度、无随机化）就是干这个的。

踩过的坑：拿**单个初始局面**测"将帅威胁项减半"，得出"省 24% 节点"；换成 50 局面套件重测，差别只有 **±3%**，方向还反过来了。单局面的节点数受 alpha-beta 剪枝的混沌影响，**不能当结论**。

另一个坑：套件里**必须有开局局面**。机动性这类"多子参与"的评估项，量级效应在开局最明显（32 个子都在场上）——只测中局会得出"没差别"。实测：机动性 UNIT=2 在**初始局面**上要 4.88M 节点才够 8 层（4.5s 预算内跑不完，只到 7 层），UNIT=1 只要 3.14M；但在 45 个中局局面上两者只差 2%。

> **⚠️ 这条实测后来被推翻了（2026-09-28）**：当时据此判断"UNIT=1 等时更快、棋力持平、改动无害"。用 `--suites 4`（各 400 局）重测，**UNIT=2 反而净胜 40 局**（四套件全为正），而且真实产品路径上的耗时几乎没变。详见「评估函数：机动性 / 子力堵塞」。**教训：单局面节点数不能当结论，量级类改动必须多套局面复核。**

### 难度阶梯验证（2026-09-27）

`LEVELS` 的深度和低档随机化参数一直没被对弈验证过。本轮用两个工具补上。

**A. 深度阶梯**（`npm run match -- --ladder`）。确定性模式会跳过失误随机与开局库，所以各档**只差深度与窗口**——测的就是纯粹的深度阶梯（20 局面 × 正反两色 = 40 局/对）：

| 上档 vs 下档 | 净胜局 | 胜/和/负 |
|---|---|---|
| 简单(d3) vs 入门(d2) | **+23** | 26 / 11 / 3 |
| 中等(d4) vs 简单(d3) | **+20** | 25 / 10 / 5 |
| 困难(d6) vs 中等(d4) | **+20** | 25 / 10 / 5 |
| 大师(d8) vs 困难(d6) | **+19** | 27 / 5 / 8 |

**阶梯单调，而且四段步长几乎一样。** 这同时给一件旧事定了性：历史上"大师与困难实际差距只有'有时多算一层'"的说法，是**大师当时跑不满 8 层**的症状（LMR / 空着裁剪 / 机动性量级修好之前，4.5s 内开局只能到 6 层）。现在大师稳定 8 层、困难 6 层，两档之间是实打实的 2 层，净胜局 +19 与其它段持平。

> **这张表是 2026-09-27 按当时的档位（2/3/4/6/8）跑的**，但它的价值在于给出了**深度差与净胜局的换算**：**每 2 层 ≈ 净 +20 局**（四段都是 2 层或 1 层，1 层那两段是 +23 / +20，也是同一量级）。2026-09-28 重定深度阶梯（改成等距 2 层的 2/4/6/8/10）就是按这个换算来的——**等距 2 层 = 难度均匀**。


**B. 走法质量审计**（`npm run level:audit`）。对每个局面先用全窗口精确搜索算出**每一手棋的真实分值**当基准，再让各档按自己的真实设置（失误概率 / 候选数 / 抖动 / 开局库）实际选一手，看它比最优手差多少分：

| 档位 | 深度 | 抖动 | 候选 | 失误率 | 平均损失 | 大漏着率 |
|---|---|---|---|---|---|---|
| 入门 | d2 | 90 | 6 | 0.35 | **187** | 29% |
| 简单 | d4 | 50 | 4 | 0.12 | **105** | 13% |
| 中等 | d6 | 0 | 1 | 0 | **9** | 0% |
| 困难 | d8 | 0 | 1 | 0 | **7** | 0% |
| 大师 | d10 | 0 | 1 | 0 | **8** | 0% |

（此表 2026-09-28 按新档位重测，基准 `--base-depth 8`。基准深度提高到 8 之后，中等/困难/大师 三档的损失都略微上抬——它们是在跟更强的参照比。）

两个读数：

- **入门 / 简单的弱主要来自随机化**（平均每步亏 187 / 105 分 ≈ 1.8 / 1 个兵，29% / 13% 的步子亏两个兵以上），不是深度。
- **中等 / 困难 / 大师 在"走法质量"上完全分不开**（9 / 7 / 8 分）：这三档的 `noise=0, topN=1, blunder=0`，参数上**只差深度**。也就是说它们**手感相同，只是算得深浅不同**。想让三档风格有别，得给中档引入别的东西（一点抖动，或不同的开局库广度）——属产品取舍，本轮没动。

**C. "给中档加抖动"这条路——试过，否决（顺带修掉一个潜伏 bug）**

既然三档质量分不开，自然的想法是给中等/困难加一点抖动（`noise`），让"犯错程度"形成梯度。实测直接踩雷：

| 配置 | 平均损失 | 大漏着率 |
|---|---|---|
| 中等 抖动 0（现状） | 5 | 0% |
| 中等 抖动 15 / 候选 2 · **窄窗口** | **288** | **51%** |
| 中等 抖动 15 / 候选 2 · 全窗口 | 5 | 0% |

原因：中等/困难/大师 的搜索是**窄窗口**的，根走法里除了最优手，其余分值都是"上界"。而 `pickByNoise` 按"分值 + 抖动"重排、**无视 `bound` 标记**，于是把上界虚高的坏棋挑了出来——**这正是「AI 择路」那个 bug 的翻版，只不过发生在随机挑选这一步**。入门/简单 之所以没事，是因为它们 `exact: true`（全窗口，分值都可信）。

- **已修**：`pickByNoise` 现在只在**可信分值**的走法里挑（一个可信的都没有才退回全体）。全窗口搜索里所有走法都可信，行为不变；`test-ai.js [15]` 压这条底线（同一局面 80 次重抖动，最大单步损失 < 150；旧行为实测可达 **944**）。
- **结论：这条路不走**。修好之后再加抖动，损失仍是 5 分——**品质一点没变**（窄窗口下"可信"的只有那几手抬升过 alpha 的走法，在它们之间挑代价极小）。也就是说"给中档加抖动"既无收益、又要求换成全窗口（更慢），所以 `LEVELS` 保持原样：**中等/困难/大师 只差深度，是设计如此**。

**D. 顺带量到：开局高度重复**

| 档位 | 首手种类 | 首手最常见占比 | 前 6 手序列种类（300 局） |
|---|---|---|---|
| 入门 | 44 | 5% | 300 |
| 简单 | 29 | 33% | 204 |
| 中等 | 10 | 43% | 35 |
| 困难 | 10 | 40% | 26 |
| 大师 | 10 | 43% | 24 |

中等/困难/大师 300 局里只有 **24~35 种开局**、43% 首手相同——开局库里"炮二平五"那条线权重 50/120 ≈ 42% 决定的。设计文档里"困难：开局变化少而精"这条差异在数据上很弱（35 → 26 → 24）。**想让开局更有变化，该动的是开局库（线路数与权重），不是档位参数**——见下一节。

## 开局库扩容（2026-09-27）

`core/book.js` 原来只有 19 条线路、首手 10 种、"炮二平五"占 38%，前 6 手序列只有 17 种——**盘盘开局都差不多**。本轮扩到 36 条：补齐了左中炮、过宫炮（两侧）、仕角炮、兵底炮、边兵，并在每个体系里加了分支（中炮对屏风马补了平炮兑车 / 五七炮 / 五六炮，顺手炮补了横车，仙人指路补了卒底炮与对兵局）。

| 指标 | 旧库 | 新库 |
|---|---|---|
| 线路数 / 覆盖局面 | 19 / 106 | **36 / 146** |
| 首手种类 | 10 | **16** |
| 最常见首手占比 | 38% | **32%** |
| 前 6 手序列种类（400 次抽样） | 17 | **36** |
| 库着中位损失 | 42 | **23** |
| 库着最大损失 | 461 | **147** |
| 单步损失 ≥200 的手数 | 9 | **0** |

**加线路必须过审计**：`npm run book:audit` 沿每条线路走一遍，把每一手和"引擎自己会选的最好手"比分数。这次就是靠它抓出一类固定错误——**车走到自己炮的后面、而那门炮又和对方的炮在同一条线上**时，对方借这门炮当炮架直接吃车（净赚一车换一炮，单步亏 450~727 分）。新加的 6 条线路全踩了这个坑，全部已修。

写线路不必手算坐标：`notation.parseText(pos, '炮二平五', MG.genLegalMoves(pos, pos.side))` 能把中文着法转成库里的坐标格式。注意字形：红 `帥仕相傌俥炮兵` ／ 黑 `將士象傌車砲卒`（写成"炮"和"砲"混了会解析失败）。`test-ai.js [7]` 钉住了"线路数 ≥ 30、首手 ≥ 12 种、最常见首手 ≤ 40%"防止以后又集中回去。

## 走法排序：全排序 + SEE 简化版（2026-09-27）

排序质量直接决定 alpha-beta 的剪枝量，也是做剪枝的前提。原来只把**前 12 手**做选择排序，其余保持走法生成顺序——那些没排过序的走法等于白搜。现在：

- **整体排序**：`orderMoves` 对区间内所有走法排序（不再只排前 K 手）。
- **SEE 简化版**：吃的子比自己便宜、且对方能回吃（车吃有根的马、炮打有保护的兵）的走法，判为"亏子的吃子"，排到**安静走法之后**——这类走法很少是好棋、子树却大。新增 `movegen.isSquareAttacked(pos, idx, bySide, skipIdx)` 支撑这一判断（用 `isChecked` 的同一套射线表，交叉验证 1292 个局面与 `isChecked` 完全一致）。
- 排序顺序：置换表走法 > 上一层 PV 走法 > 划算的吃子(MVV-LVA) > 杀手走法 > 安静走法(历史启发 + 位置增益) > 亏子的吃子。

效果（开局，本机 node）：depth 6 节点 978k → 803k，depth 7 4.26M → 4.26M，depth 8 22.1M → 24.3M——**单看排序本身收益不大**，但它是下面那件事的前提。

## AI 择路：可信分值 vs 上界（2026-09-27）

非全窗口搜索里，只有真正抬升过 alpha 的根走法拿到的是**可信分值**，其余只是**上界**（可能恰好等于当时的最优分）。旧版把两者混在一起按分值排序、同分再按走法编码取小，于是「上界虚高 + 编码小」的坏棋会中选——实测抓到一手白丢马的着法：全窗口精确分 −365（40 手里排 37），非全窗口却给它 +26 并让它中选。低难度用的是 `exact` 全窗口，所以不受影响，这正好解释了「难度越高反而下得越糟」。

现在 `searchRoot` 与 `createSearch` 都给这类走法打 `bound` 标记，排序时排到可信分值之后，两者不再比大小。回归用例见 `test-ai.js` [14]（送马局面在 normal/hard/master 下都不得中选；分片路径因 LMR/空着裁剪仍会中选，属已知局限，见「评估函数：机动性」一节）。

**这项修复的实际分量（2026-09-27 消融复核）**：把它单独关掉，当前版本在确定性对抗里 **116 胜 2 和 0 负**（118 局，深度 6；深度 5 是 109 胜 9 和 0 负）——是**项目史上最有价值的改动**，远超过任何评估项。当年那次"修复后 0 胜 6 负"的等时对抗结论是错的，详见「历史结论复核」。

**同一个坑还埋着一处（2026-09-27 补修）**：`pickByNoise`（随机挑选 `noise`/`topN`）当时也按"分值 + 抖动"重排，**没看 `bound` 标记**——窄窗口搜索里它会把上界虚高的坏棋挑出来。之前一直没暴露，只因为中/高/大师档恰好都是 `noise=0, topN=1`（走不到那条分支）。现在 `pickByNoise` 只在**可信分值**的走法里挑，回归用例 `test-ai.js [15]`。详见「难度阶梯验证」C 节。

## 剪枝：晚走法削减（LMR）+ 空着裁剪（NMP）（2026-09-27）

**LMR**：门槛 depth ≥ 4、跳过前 4 手、削减 1 层，抬升 alpha 则按原深度补搜。上一轮在没有全排序时开它是 **0 胜 4 负**，全排序后重开是 **4 胜 2 负**——"先把排序做扎实再谈剪枝"这个判断被验证了。

**NMP**：上一轮用 depth ≥ 3 / 削减 2 层试过，**0 胜 4 负**——那时"空着"后的搜索落在 depth ≤ 0，只剩静态搜索，"我不走对手也翻不了盘"这个判断太廉价。这一轮门槛提到 **depth ≥ 5**（空着后至少还搜 2 层），保留"不是将军 / 不连续空着 / 子力 ≥ 9"的护栏，且空着搜索内部不参与重复局面记账：等时对抗（产品路径，6 局）**3 胜 1 和 2 负**。

两者叠加的速度（开局）：depth 6 807ms → **332ms**，depth 7 2657ms → **985ms**，depth 8 22900ms → **3037ms**（节点 -80%）。

## 将军延伸：水平线上的将死必须被看见（2026-09-28）

静态搜索（`quiesce`）只生成吃子（`genPseudoMoves` 的 `capturesOnly`），所以碰上**"被将军但没有吃子可走"**的局面时 `end === start`，直接返回静态评估——等于**没看见自己被将**；更糟的是，**被将死 / 困毙也会被当成普通局面估分**。这是水平线效应里最要命的一种。

修法：被将军时不下沉到静态搜索，改为再搜一层（`depth = 1`），让应将被真正搜到。护栏：`ply` 接近 `MAX_PLY` 时不再延（避免连将把搜索拖爆）；空着搜索里不延（空着之后的"被将"不是真实局面）。

实测（同一局面：红方一步杀，俥(4,2)→(4,1)，将被两马封住、俥有保护）：

| 搜索深度 | 修复前 | 修复后 |
|---|---|---|
| 1 | 分值 11308、**mateIn=0（没看见杀）** | **分值 99999、mateIn=1** |
| 2 | 分值 99999、mateIn=1 | 同上 |

**成本与棋力**：50 局面套件（`npm run node:bench`）节点 **+3.1%**（8.26M → 8.52M）；确定性对抗深度 6 **净 +8**（90 局）、深度 7 **净 +1**（50 局）——棋力上测不出增益（安静局面里水平线将死本来就罕见），但**它修的是正确性**：引擎不会再漏掉贴边的杀。回归用例 `test-ai.js [16]`。

## 搜索三件事：应将生成 / futility / 期望窗口（2026-09-28）

**① 静态搜索里的完整应将生成（采纳）**。上一轮的将军延伸只兜住了 `depth = 0` 那一层；吃子交换里再将军（`qply ≥ 1`）时 `quiesce` 仍然只生成吃子，会把走将 / 垫子这类应法全漏掉。现在 `quiesce` 检测到被将军就生成**全部合法走法**，并且不做"站着不动"的 stand-pat（`best` 从 `-INF` 起；增量剪枝那条也加了 `!inCheck` 护栏，否则 `-INF` 会把所有走法都跳掉）。代价：节点 **+3.3%**（8.39M → 8.67M）；对抗深度 6 **净 +7**（90 局）——棋力持平，属正确性修复。

**② 无用着削减 futility（采纳）**。`depth == 1` 且不在将军时，若 `静态评估 + 200 ≤ alpha`，安静走法几乎不可能翻盘，直接跳过、不展开子树（吃子不跳、第一手不跳、将军时不跳、alpha 已是杀棋分时不跳）。节点收益随深度增大：

| 深度 | 无 futility | 有 futility | 降幅 |
|---|---|---|---|
| 6 | 4.65M | 3.17M | −32% |
| 7 | 15.99M | 9.86M | −38% |
| 8 | 44.26M | 22.91M | −48% |

墙钟只省 23%（每个 depth-1 节点要多算一次静态评估）。对抗深度 6 **净 −2**（90 局）——固定深度下持平，**这正是速度类技术的特征：等深度不变、等时更强**。效果：大师档 25 个局面里跑到 10 层的从 9 个变成 12 个。

**③ 根节点期望窗口 aspiration（试了，回退）**。以「上一层分值 − 150」为下沿开窄窗，全落空就退回 `-INF` 重搜。实测节点 **5.22M → 5.21M（−0.2%）**——等于没有。原因：**根节点本来就是"滑动零窗口"**（每一手都按当前 alpha 开窗，而 alpha 最终都会涨到最优分），所以后面走法的截断条件完全一样；唯一不同的是第一手的窗口，而第一手是上一层的 PV、本来就该搜全。（把窗口收到 10 验证过它确实生效：节点反而涨到 5.57M——频繁失败重搜。）

## 剪枝的边界：LMR 参数化（采纳）vs 更激进的剪枝（否决）（2026-09-28）

**① LMR 削减层数改成随"第几手 + 节点深度"递增（采纳）**。原来固定减 1 层；现在第 10 手之后、或节点深度 ≥ 8 时再多减 1 层（越靠后、越深的安静走法越不可能好）。

| 指标 | 结果 |
|---|---|
| 节点（50 局面套件 d8） | 22.91M → **16.66M（−27%）** |
| 墙钟（同上） | 27.4s → **20.5s（−25%）** |
| 固定深度对抗 d6 | **净 +2**（90 局）——持平 |
| 大师档 30 局面里达到 10 层 | 14/30 → **16/30** |
| 大师档中位用时 | 2948ms → **2146ms** |

棋力持平、快 25%、等时下还更深——"速度类技术"该有的样子。

**② depth-2 futility + razoring（否决）**。把 futility 从 depth 1 扩到 depth 2（余量 400），并加 razoring（评估差 400 就直接下沉到静态搜索、够不着 alpha 就交差）：

| 指标 | 结果 |
|---|---|
| 节点（d8） | 22.91M → 20.43M（−11%） |
| 墙钟 | 27.4s → 25.5s（−6%） |
| 固定深度对抗 d6 | **净 −12**（90 局）——**明确退步** |

省下的节点抵不过准确度的损失，**两项都已回退**。教训：**剪枝不是越多越好**——depth 1 的 futility 之所以成立（净 −2、省 23% 时间），是因为它只砍最没希望的那一层安静走法；再往下砍就开始伤棋。

（过程中的一个教训：中途有个对照搞错了——变体是在**还带着这两项激进剪枝**时建的，于是 LMR 的收益被高估成"−40% 节点 / 21 个局面到 10 层"。**改多项时一定要从干净基线重建对照**，否则会把别人的功劳算到自己头上。）

## 评估侧：子力协调（试了，回退）（2026-09-28）

**设计**。象棋里"有根 / 无根"很实在：无根的车马炮被一攻就得逃，白丢一步先手。但完整的攻击图会让评估贵 2~3 倍——而评估在每个叶子节点都要跑，成本是硬约束。所以这里数的是**保护关系数**（己方车/炮各保护了几个己方子）：它可以在机动性那趟射线遍历里顺手算出来，不用额外扫盘。炮的保护要"恰好一个炮架"——射线上的第一个子是炮架、第二个若是己方才算。

**成本**：直接测评估吞吐（40 万次调用）——**1.54M 次/秒 → 1.24M 次/秒（−17%）**。注意**不能用节点数衡量评估成本**：评估的**取值**变了会改变搜索树形状，节点数会跟着乱跳（实测同一个改动，节点数一次 +2%、一次 +8%，都不代表开销）。

**效果：多套局面交叉验证后确认无效，已回退。**

一开始用单套局面（200 局）测，四个量级各一轮，结果自相矛盾：

| 对照 | 净胜局 |
|---|---|
| 4 分 vs 关掉 | +14 |
| 4 分 vs 2 分 | −15（即 2 分更好） |
| 2 分 vs 关掉 | −9（即关掉更好） |
| 4 分 vs 6 分 | −8（6 分略好） |

前三条构成**循环**（4 > 0、2 > 4、0 > 2），逻辑上不可能同时成立——那个"+14"是假信号。

于是给 `match.js` 加了**多套件模式**（`--suites N`：N 套不同种子的局面、子进程并行，最后判读"是否全部同号"），用它重测（4 套 × 50 局面 = 400 局）：

| 套件 | 1 | 2 | 3 | 4 | 合计 |
|---|---|---|---|---|---|
| 净胜局 | −8 | +8 | −3 | 0 | **−3** |

**有正有负 → 效应落在抽样偏差之下，判不出来。** 加上它让评估慢 17%，整项回退。

**工具校准**：拿「关掉根走法择路」这个已知的**强正效应**跑同一套流程——两套局面各 **+38 / +40**（合计 +78 / 80 局，全部同号）——说明工具对真效应敏感、对噪声会判"判不出来"。

## 对抗怎么测才可信（2026-09-28）

**单一局面套件的结果受"局面抽样偏差"影响，不是随机噪声。** 实测：拿"LMR 递增 vs 基线"这个对照换一套局面（同 200 局、种子 777）重跑，结果从 **+2 变成 −5**；多套件模式里每套 100 局的摆动更是到了 **±8**。

所以判定一个改动要这么做：

1. **用 `--suites`（≥3 套）**：`node scripts/match.js <对照> --depth 6 --positions 50 --suites 4` = 4 套 × 100 局 = 400 局，子进程并行，约 15 分钟。
2. **看判读行**：只有"全部同号"才算方向可信；出现"有正有负"就是**效应落在抽样偏差之下**，别硬下结论——子力协调那项就是这么被否掉的（单套测出 +14，多套一测是 −3）。
3. 单套模式下 **|净| < 10 基本不能当信号**（原先"净 ≥ 10"的经验阈值对 100~200 局偏松）。
4. 搜索类改动（剪枝、置换表）比评估类稳定得多，单套结果通常可信；**评估类改动会与具体局面交互，必须多套复核**。

**判读带统计（2026-09-29 加强）**：`--suites` 的报告会同时给**跨套件标准差**和**合计净的 95% 区间**（t 区间；套件之间是不同局面、相互独立）。只看符号一致性太保守——4 套下"3 正 1 负"和"4 套全 0"都会被判"判不出来"，但证据强度差很多。判读分四档：

| 判读 | 含义 |
|---|---|
| 区间全在 0 以上 / 以下 | **效应可信** |
| 符号全同但区间跨 0 | 方向可疑，样本还不够 |
| 区间跨 0 且有正有负 | 效应落在抽样偏差之下，判不出来 |
| 各套件全为 0 | 无差别 |

**分辨率**：4 套（400 局）能可靠判出**约 ≥ 35 局（9%）**的效应——机动性 UNIT=2 的 +40 正好卡在这个门槛上。要判 **~+20 局（5%）**量级的效应得用 8 套（800 局）。

### ⚠️ 判读尺子必须中立（2026-09-29 重大修正）

`match.js` 的 `material()`（手数上限后按子力判胜负）原来读的是**被测仓库的** `PIECE_VALUE`——于是**尺子会随候选一起变**：候选抬高自己的兵值 → 判读也用抬高后的兵值 → 它囤的兵更"值钱"。做兵值扫描时这就成了**自我实现的循环**。

**实际后果**：用这把尺子扫兵值，得到一条"单调上升、看不到峰"的曲线（70→100 +51、→130 +96、→170 +124、→220 +173、→300 +280，每一级都"95% 区间全在 0 以上"）。**把尺子固定成中立表（象棋传统价值比 车9 / 炮4.5 / 马4 / 士象2 / 兵1）之后，结论完全反转**：

| 对照 | 中立尺子下的净胜局 | 判读 |
|---|---|---|
| 300 vs 220 | **−328**（八套全负） | 300 明显更差 |
| 70 vs 220 | **+314**（八套全正） | **原值 70 明显更好** |

所以那次扫描整体作废。**用中立尺子重扫**（各 600 局）：

| 对照 | 净胜局 | 95% 区间 | 判读 |
|---|---|---|---|
| 50 vs 70 | **+47** | 9 ~ 85 | 50 更好（可信） |
| 70 vs 100 | +22 | −3 ~ 47 | 判不出来 |
| 70 vs 220 | **+314** | 266 ~ 362 | 70 明显更好 |
| 50 vs 30 | −14 | −59 ~ 31 | 判不出来 |
| 50 vs 10 | +9 | −34 ~ 52 | 判不出来 |

即曲线是 **10 ~ 70 的一段平台，原值 70 已经略微过峰**。所以兵值 70 → **50**（小改，+47/600 ≈ 7.8%）。

**注意方向**：有偏差的尺子把结论指向"往上抬到 300"，真相是"略微往下调到 50"——**尺子偏了不只是幅度不准，方向都能反过来**。

**教训：对照的判据不能依赖被测对象。** 已把 `material()` / `totalMaterial()` 改成固定的 `ADJ_VALUE` 中立表，以后所有对抗都用它。（影响范围：只有改 `PIECE_VALUE` 的改动会踩这个坑——机动性量级、子力协调、残局马炮调整都没动子力价值，结论不受影响。）

## 套件里没有残局 + 残局马炮调整（2026-09-28）

**发现：局面套件全是中局。** 查了套件的子力和分布——50 个局面**全部 ≥ 2200**，也就是说残局相关的评估项（兵值缩放、马炮残局调整、残局系数）**从来没被走到过**；历次测"残局项"测到的其实只是搜索树深处偶然跌破阈值的节点。

**修生成器时踩了一串坑，都值得记住：**

1. 第一版用"随机走 40~70 手"生成残局——**纯随机走几乎不减子力**（实测 3000 次全部 > 3500），一个都生成不出来。
2. 第二版改成"优先吃子地走"——又会一路换到底，把车马炮全换光（只剩"士×2 象×4 兵×6"），**马炮残局调整照样走不到**。
3. 最终版：**从初始布局按类型成对删子**（双方保留同样数量 → 天然均势），并要求至少留一个攻子。既能控子力总量，又保证马炮在场。
4. **`--suites` 没把 `--endgame` 传给子进程**——所以所有"多套件 + 残局"的跑法其实都是**纯中局**，两次跑还给出了一模一样的结果（正是这个巧合让我起疑）。现在补上了，并在报告里核对实际局数（生成不足会打 ⚠）。

**修正后的实测**（生成器修好、且 `--endgame` 确实传给子进程之后；`--positions 25 --endgame 25`）：

| 改动 | 各套件净胜局 | 合计 | 95% 区间 | 判读 |
|---|---|---|---|---|
| 残局阈值 2200 → 3000 | −2 −1 −3 −3（400 局） | **−9** | −14 ~ −4 | 2200 更好（可信） |
| 兵在残局的 PST 放大 0.6 → 1.2 | 0 +6 −6 +4（400 局） | +4 | −25 ~ 33 | 判不出来 |
| 残局马炮调整 ±80 vs 关掉 | 0 +1 0 +1 −1 0（600 局） | +1 | −4 ~ +6 | 判不出来 |

即**三个残局旋钮的现值都合适**：阈值 2200 显著优于 3000；兵值缩放与马炮调整都判不出差别（马炮调整留着——它修的是方向性错误、零成本）。注意阈值那条的跨套件标准差只有 **1.0**，所以 −9 这种小效应也能判定。

**⚠️ 这一节之前的两版"实测"都是无效的**，坑法还不一样：

1. 第一版用"随机走 40~70 手"生成残局——纯随机走几乎不减子力，**一个局面都生成不出来**（`--endgame` 是空操作）。
2. 第二版生成器修好了，但 **`--suites` 没把 `--endgame` 传给 fork 的子进程**——所以"多套件 + 残局"其实都是纯中局，两次跑还给出一模一样的结果。

**这是本项目第三次被工具坑到**（前两次：单局面节点数、判读尺子不中立）。共同教训：**改完工具必须核对"实际生效/实际局数"，不能只看标签**——现在 `--suites` 的报告会核对局数并打 ⚠。

**残局马炮调整留着**：它修的是**方向性错误**——原来残局给马贬值，注释还写"马缺少炮架配合"，把马炮的特性记混了；常识是**"残局马胜炮"**（炮要靠炮架，残局炮架难找）。成本为零，实测在 depth 6 下不改变任何决策、也无害。**残局阈值不动**（3000 判不出来）。

## 难度档位的深度上限重定 + 预算预判 + PVS（2026-09-28）

**问题**：`LEVELS` 的时限是当年按慢引擎定的，几轮搜索优化（全排序 + LMR + 空着裁剪 + TT）之后引擎快了一个量级。实测各档只用掉预算的一小部分（25 个局面）：

| 档位 | 深度上限 | 时限 | 实际中位用时 | 撞到深度上限 |
|---|---|---|---|---|
| 中等 | 4 | 1500ms | **19ms** | 25/25 |
| 困难 | 6 | 2600ms | **133ms** | 25/25 |
| 大师 | 8 | 4500ms | **1121ms** | 25/25 |

也就是说**卡住强度的是深度上限，不是速度**——每个档都"算完了在干等"。

**改动一：大师档 8 层 → 10 层**。中局现在稳定跑到 **9 层**（3.7s），开局仍是 8 层（9 层在 4.5s 内跑不完）。按「难度阶梯验证」测出的"2 层 ≈ 净 +20 局"，这是实打实的增益。

**后续（2026-09-28 同日）**：中等/困难 两档的预算余量更大（1% / 5%），最后也一起抬了——把整条阶梯定成**等距 2 层：2 / 4 / 6 / 8 / 10**（原来 2 / 3 / 4 / 6 / 8）。依据是同一句换算（2 层 ≈ +20 局），所以等距 = 难度均匀；时限不变，实测各档中位用时 95ms / 106ms / 656ms / 2097ms，都留着余量。详见 `docs/玩法设计.md` 的档位表。

**改动二：预算预判**（`NEXT_DEPTH_FACTOR = 2.5`）。原来只要没到时限就开下一层，开了被砍掉结果作废——**白等一场**。抬上限后这个问题变明显：大师开局跑完 8 层用了 2.6s，接着开 9 层、4.5s 到点被砍，那 1.9s 完全白费。现在上一层耗时 × 2.5 超过剩余预算就不开。效果：大师开局 4501ms → **2568ms**（层数不变），中局仍拿得到 9 层。

**改动三：PVS（零窗口试探）**。原来内部节点对**每一手都用全窗口**搜。现在只有第一手用全窗口，其余先用 `(alpha, alpha+1)` 窄窗口试探、真的抬升 alpha 才全窗口重搜（依赖排序质量：全排序 + 置换表走法 + 杀手 + 历史撑着）。实测 50 局面套件节点 **8.52M → 8.39M（−1.5%）**，确定性对抗深度 6 **净 +5**（90 局）——收益比预期小得多（排序已经够好，多数节点在前一两手就截断），但它是标准积木、无副作用，留着。

**代价与取舍**：大师档中局每步从约 1.2s 变成约 3.7s（仍在上限 4.5s 内）。这是把设计早就分配给大师档的预算真正用起来；嫌慢就把 `LEVELS.master.time` 调小（例如 3000ms 会让它多半停在 9 层）。

## 分片搜索的根走法：查清了根因，但"修"是净亏（2026-09-27）

上一轮留下的已知局限（分片路径在送马局面上选中坏棋）本轮查到了根因、也把修法做出来测了，**结论是不该修**，过程记录如下。

**根因**：`createSearch` 每片只搜一个根走法，被切片打断的走法沿用上一层（更浅）的旧分。深度越大打断越多——实测那一局在 depth 6 时**整层 40 手全被打断**，所有分值都是旧分，"哪手更好"完全不可比，坏棋（分片给 +61、全窗口精确分 −314）就这样中选。同步搜索 `findBestMove` 不受影响，因为它整层作废、沿用上一层完整结果。

**试过的修法**：整层作废 + 下一片重试同一层（只重搜被打断的那几手，已拿到的可信分连同 `curAlpha` 一起带上，避免整层重做）。修完两条路径给出**同一手同一分**，但：

| 版本 | 开局层数 | 中局层数 | 等时对抗（6 局） |
|---|---|---|---|
| 旧（沿用旧分） | 7 | 8 | — |
| 新（整层作废 + 重试） | 6 | 7 | **新 0 胜 6 负** |

重试会把被打断走法的子树重做一遍（中局节点数 126 万 → 446 万），把切片从 12ms 调到 100ms 也救不回来。**深度比"分值可信"更值钱**，所以这次改动已回退，测试里的断言保持"同步路径必须不选中 + 分片走法合法"的形态（`test-ai [14]` 会打印一行提示）。

**顺带发现**：置换表从 2^16 放大到 2^18，**同步**搜索在开局就能跑满 8 层（4.4s / 480 万节点），但**分片**路径毫无受益（仍 6–7 层），所以没改——4 倍内存不值。

**真正的解法（留给后续）**：① 把搜索放进 Worker（小程序支持 `wx.createWorker`），搜索就能用同步版本，分片问题自然消失；② 或者让搜索"可暂停可续跑"（显式栈机 / 生成器），重试就不必重做。在那之前，产品路径按现状（深一层、偶有旧分）是实测更强的选择。

## 评估函数：机动性 / 子力堵塞（2026-09-27，2026-09-28 修正量级）

象棋里"子力互相堵塞"是很实在的弱点：马腿被塞住，那个方向的两个落点直接废掉；车炮被自家子堵在角落里，摆着发挥不出作用。两项都很便宜，折进位置价值那一趟扫描：**马腿**四个方向各看一格（每个被塞折算 3 格机动性）；**车/炮**沿四个方向数空格，每方向最多数 3 格、每格 `MOBILITY_UNIT` 分。只数前几格是有意的——评估在每个叶子节点都要跑，为"精确机动性"遍历整条线不值。

**⚠️ 量级：2026-09-28 推翻了 09-27 的结论。** 09-27 曾以"每格 2 分和位置表（±20）同量级，等于让线路通畅度盖过位置本身、节点暴涨、等时掉一层"为由把它压到 **1 分**。这个论据站不住：

- "节点暴涨"是**单个初始局面**测的（343 万 → 647 万）。后来查明**单局面节点数受剪枝混沌影响、不可信**；换成 50 局面套件（`npm run node:bench`），两者总节点只差 2%。
- 当时的棋力对照（d5 +9 / d6 −8，"持平"）是**样本不足的假阴性**。

用多套件复核（`--suites 4`，各 400 局；判读看"是否全部同号"）：

| 对照 | 各套件净胜局 | 合计 |
|---|---|---|
| **UNIT=2 vs 1** | −18 −10 −7 −5（四套全负 ⇒ 2 分胜） | **2 分胜 40 局** |
| **UNIT=3 vs 1** | −8 −9 −11 −4（四套全负 ⇒ 3 分胜） | 3 分胜 32 局 |

**峰在 2 分**（也就是原设计值）。已恢复成 2。真实产品路径上的代价可以忽略——各档中位用时 102 / 142 / 722 / 2098ms（原 95 / 106 / 656 / 2097），而大师档跑到 10 层的局面反而从 13/25 变成 **14/25**。

**教训**：这是本项目**第二次**被"单局面节点数 + 样本不足的对抗"误导（第一次是把 LMR 的收益算成 −40%）。**量级类改动必须用 `--suites` 多套局面复核。**

其余实测（每格 2 分时代的数据，供参考）：

- 每格 2 分 **净 +28** 胜"完全不加机动性"（固定深度 6）——机动性值得留，且优势随深度增大（深度 5 时只有 +5）。
- 每方向数 3 格与数 2 格**净 0**——格数不是关键，量级才是。

**已知局限**：加上机动性项后，分片搜索（产品实际走的路径）在 `test-ai [14]` 那个送马局面上会选中坏棋，同步路径不会——根因不在评估项，而在分片搜索的根走法处理，见下一节。曾尝试过整层作废+重试的修法，修完两条路径给出同一手同一分，但分片路径会掉一层深度、等时对抗 **0 胜 6 负**，深度比"分值可信"更值钱，所以代码保持现状，只在测试里打印提示。

另有一条实测：**加深搜索救不了棋力问题**。把大师档时限放大到 12 秒/步（稳定跑到 7–8 层，57 手里 30 手完成 8 层）后，它**仍然**输给「简单」两局，子力亏 2–3 车。所以「大师输给简单」的主因不在深度，也不在择路——择路修复后局面评估变准了，但引擎的**评估函数**（只有子力 + 位置表，没有王安全、威胁、机动性）才是真正的天花板。下一步要提升棋力，应该从这里入手。

## 评估函数：将帅安全 + 缺士怕车 + 不甘心和棋（2026-09-27）

`core/evaluate.js` 原来只有子力 + 位置表 + 一点士象加成，象棋最要紧的**将帅安全**完全没算。补了三项，全部折进已有的两趟棋盘扫描，不额外遍历：

- **攻子威胁九宫**：马/车/炮（以及兵）按"到对方将帅的切比雪夫距离"给威胁分，**同一列/同一行再加权**——车无遮挡、炮恰好一个炮架才算真能直取（沉底车 / 当头炮 / 卧槽马 的近似），被挡住减半。
- **缺士怕车、缺象怕炮**：士象的边际价值随对方攻击子力缩放（一个士对上一门车才值钱；双方都剩单车寡炮时缺士象并不致命）。原来的固定 `士象数 × 12` 已替换。
- **不甘心和棋**：重复局面判和的分值从 0 改成 `REPETITION_DRAW = -120`（约 1.7 个兵）。给 0 会出大问题——引擎只要算出自己略微落后（-30 之类）就去往返走子凑重复和棋，对手不配合时白挨打。实测：**关掉重复判定后大师能赢「简单」，开着却输/和**。给 -120 的含义是"只有明显落后才认和"，真被压住了（-600）仍然会接受和棋。

效果（**表里的数字当年只有 4 局样本，2026-09-27 用 `npm run match` 复核后打了问号，见「历史结论复核」**）：

| 指标 | 结果 | 复核（确定性对抗） |
|---|---|---|
| 等时对抗（产品路径 createSearch，master 1500ms/步，4 局） | 新评估 **2 胜 1 和 1 负** | 4 局等于没测 |
| 威胁九宫关掉 | — | 深度 6 **+3**（90 局）/ 深度 7 **+10**（48 局）——测不出可靠价值 |
| 缺士怕车关掉 | — | 深度 6 **−1**（90 局）——测不出 |
| 和棋分改回 0 | — | 深度 6 **+2**（90 局）——测不出 |
| 开局 depth 8 耗时 | 37s → **23s**（评估更准 → 走法排序更好 → 剪枝更多，顺带省了 40% 时间） | 仍成立 |
| 开局 depth 6 / 7 | 1.25s → 0.89s / 4.9s → 2.7s | 仍成立 |

## 杀法识别

绝杀时会判出杀法名（如「马后炮」），既写进终局文案，也朗读出来。实现在 `core/mate.js`。

**只覆盖名字能从终局还原的那一类**，共 15 种，分两类：

| 类别 | 数量 | 名字在描述什么 | 名单 |
|---|---|---|---|
| **几何型** | 11 | 终局形态，判据唯一 | 对面笑、马后炮、重炮、闷宫、双车错、卧槽马、挂角马、钓鱼马、侧面虎、二鬼拍门、闷杀 |
| **阵形型** | 4 | 攻杀阵形，天然会与几何型重叠 | 天地炮、夹车炮、铁门栓、海底捞月 |

两类都不认的，是名字描述**过程**或**威胁**的那些，终局里已无从还原，**一律不猜**——认不出时返回 `null`，文案退回「绝杀无解」：

- 讲「怎么杀的」：大胆穿心、炮碾丹砂、送佛归殿、老兵搜山、拔簧马、双马饮泉
- 讲「阵形威胁」：**空头炮**——炮与将同一直线、中间无子，看着像，但炮要炮架才能吃子，没有炮架它既将军不了也封不住格子，在终局里是个旁观者。实测把那一枚炮整枚拿掉，局面**照样是将死**，足以证明它没参与这一杀

这也是阵形型里另外 4 种能命名、空头炮不能的原因：**那 4 种的棋子都实打实参与杀**（两炮都在将军 / 车真的封了口 / 中炮正是士不敢吃车的原因 / 将军子确实沉在底线）。

### 阵形型与几何型撞名怎么解

同一个终局可以既像闷宫又像天地炮，这不是技术问题而是语义重叠。解法**不是拍一张优先级表**，而是给判据补上区分性条件，让每种各归各位：

- **闷宫要求「单炮将军」**——中炮与沉底炮同时将军是天地炮，不是闷宫
- **重炮要求「无车参与」**——双炮并线时若有车配合封口，那是夹车炮

剩下少量顺序依赖，用 `mate.js` 里 `MATCHERS` 数组的排列显式表达：越具体的排越前。`test-mate.js` 的 [8] 节把每条区分条件都钉住（含反向用例：有车占将门但没有中炮时归双车错，不归铁门栓）。

### 各杀法的判据要点

- 炮系看**炮架是谁**：己方马→马后炮；己方炮→重炮；敌士且将紧贴→闷宫；其他敌子→闷杀
- 马系查**「路 × 横线」换算出的精确格位**
- 车系要求**另一车确实攻击将的相邻格**（只数「还有一辆车」会把单车杀误判成双车错）
- 天地炮＝中炮在将的纵线 ＋ 沉底炮在对方底线；夹车炮＝双炮并线 ＋ 有车参与
- 铁门栓＝中炮 ＋ 车/兵占住将门（将正前方那格）；海底捞月＝将军子沉在底线正对将背后（将不在底线）

判据依赖一套坐标记法（攻击方看「路」，防守方看「横线」），马位术语因此都是精确格位：

```
路   = 攻击方纵线编号：红攻黑时 路 = 9 - file；黑攻红时 路 = file + 1
横线 = 防守方横线编号：黑守时 横线 = rank + 1；红守时 横线 = 10 - rank

卧槽马 (2,1)/(6,1)   挂角马 (3,2)/(5,2)   钓鱼马 (2,2)/(6,2)   侧面虎 (2,3)/(6,3)
```

`result` 上会多出 `mate`（中文名）与 `mateKey`（ASCII key，供语音等资源引用）两个字段。

**闷宫与闷杀的分界**：闷宫的炮架**一定是对方的士**，且将紧贴炮架；炮架是士以外的子力（或将已离位）就是闷杀。两者常合称「闷将杀」。

### 多音字

朗读用的文本不等于显示名——象棋术语里多音字不少，TTS 会挑最常用的读音，往往不是术语那一个。`MATE_PATTERNS` 里的 `speech` 字段用**同音字**把读音锁死（显示仍是原字）：

| 术语 | 正确读音 | TTS 默认 | 朗读文本 |
|---|---|---|---|
| 重炮 | chóng（叠炮） | zhòng ✗ | 虫炮 |
| 双车错 | jū（象棋里的车） | chē ✗ | 双居错 |
| 夹车炮 | jū | chē ✗ | 夹居炮 |

改法：在 `core/mate.js` 对应条目加 `speech`，再跑 `npm run gen:voice`。

**生成脚本是增量的**：它读一份 `audio/mate-voice.json` 朗读文本清单，文本没变就跳过。这是必须的——`afconvert` 出来的 m4a 是非确定性的（同一段文本连跑两次字节就不同，但解码后 PCM 完全一致，差的是容器元数据），不做跳过的话每跑一次都会把全部文件标记成已修改。要强制全量重生成用 `npm run gen:voice -- --force`。

**没有耳朵也能验收**：`say` 出来的音频可以解成 PCM 做基频曲线分析，用声调走向判断读的是哪个音——二声（阳平）先微降后上扬，四声（去声）单调下降。改「重炮」时就是用这个方法确认的（旧版第 1 音节 327→204Hz 单调降＝zhòng，新版 208→94→208Hz 先降后扬＝chóng）。

## 棋盘标记

棋子身上的标记只有两套，**共用同一种光晕形状、只换颜色**——一个说「刚动的是这枚」，一个说「这几枚正被盯着」，必须一眼分得开：

| 标记 | 颜色 | 含义 |
|---|---|---|
| 上一步走的子 | 琥珀 `#e9a834` | 刚落定的那枚，落子瞬间光晕更大更亮再回落到常亮 |
| 被威胁的子 | 绛红 `#c62030` | 当前走棋方的子中，对方能吃掉的 |

**被威胁的判据是「当前走棋方的子中，对方有合法吃子能落到它身上」**，不做子力得失过滤：等价兑子、乃至亏子换都算。宁可多标，不替玩家判断值不值。

由此有两个直接后果，都是有意为之：

- **开局就会亮两枚**——黑炮隔着红炮能打到红马（`炮二进七` 那一路），这是真实存在的吃子，不是误报
- **同一局面被威胁的子可能有好几枚**，全部统一用同一个绛红，不按子分色

**只在局面变化时算一次**（走子 / 悔棋 / 重开 / 联机重同步），不放进每帧的渲染路径：它要把对方的合法走法整批生成一遍，逐帧算太贵。

### 15 种杀法的母题（底衬）

母题要回答的是「**这一招凭什么成立**」，所以每种都点在自己的关键处：

| 杀法 | 母题 |
|---|---|
| 马后炮 | 将军线由炮经马扫向将，扫到马身时脉动一圈（点出「马是炮架」） |
| 重炮 | 同上，但炮架处脉动**两圈**（点出「两炮」） |
| 闷宫 / 闷杀 | 先扫将军线，再把将四周四道短线**合拢成框**（被自家子堵死） |
| 双车错 / 天地炮 / 夹车炮 | 各子**错开一拍**各拉一条线指向将（两条 / 两条 / 三条） |
| 卧槽马 / 挂角马 / 钓鱼马 / 侧面虎 | 从马到将画一条**「日」字轨迹**（先长边后短边），落点闪一下 |
| 对面笑 | 两帅之间一道**光柱**贯穿 |
| 二鬼拍门 | 两条封线从两兵向外拉开，**锁住两条肋道** |
| 铁门栓 | 将门上**落下一道门闩**，车与中炮各拉一条线 |
| 海底捞月 | 底线那条将军线 ＋ 一弯**月弧**从将的下方兜上来 |
| 认不出杀法 | 不画母题，只压暗 + 落款「绝杀」 |

母题靠 `mate.js` 返回的几何驱动（`checker` / `screen` / `king` / `pieces`），不是硬编码局面。
`test-endgame.js` 对每种杀法都断言**母题的第一笔落在预期的关键子上**——演出画错位置比不画更糟。

## 操作

- 点选：先点己方棋子再点绿色落点；拖拽：按住拖到落点松手（拖拽中高亮落点）。
- 工具栏（自绘于棋盘下方）：悔棋 / 提示 / 翻转 / 重开 / 菜单；联机时悔棋与重开禁用。
- 规则页支持上下拖动滚动。
- 系统设置（菜单最下方）：音乐开关 / 配乐切换（松风·桂月）/ 音效开关 / 先后手（执红·让先执黑）/ 主题（松桂·紫金夜）。

## 规则实现

将死与困毙均判负；长将判负；三次重复判和；连续 120 手无吃子判和；将帅不照面。
